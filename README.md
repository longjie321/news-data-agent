# 新闻数据智能体（News Data Agent）

用自然语言查询新闻数据的 AI Agent 服务 —— **模型自己决定调哪个工具、调几次**。

手写 Function Calling，未使用 LangChain 等 Agent 框架。

---

## 一句话说明它和"普通接口"的区别

| | 普通接口 | 本项目 |
|---|---|---|
| 谁来定流程 | 代码写死（先查 A、再查 B） | **模型自己判断** |
| 一个问题要不要分几步 | 不会，一次查完 | 会，**它自己拆步骤** |
| 出错怎么办 | 报错返回 | 把错误交回模型，**它自己换个做法重试** |

---

## 技术栈

| 层 | 用了什么 |
|---|---|
| Web 框架 | FastAPI |
| 数据库 | MySQL + SQLAlchemy 2.0（全异步，aiomysql 驱动） |
| 大模型 | DeepSeek `chat/completions`（Function Calling / 工具调用） |
| 流式推送 | SSE（Server-Sent Events），六类事件 |
| 前端 | 原生 HTML + CSS + JavaScript（单文件，无框架） |
| 数据校验 | Pydantic v2 |
| 测试 | pytest + pytest-asyncio |
| 部署 | Dockerfile + docker-compose |

## 它是怎么跑的

```
                    ┌─────────────────────────────────┐
   用户提问  ────────▶│  1. 把问题 + 工具清单发给模型    │
                    │     （非流式，只为拿到决定）      │
                    └───────────────┬─────────────────┘
                                    │
                    ┌───────────────▼─────────────────┐
                    │  2. 模型说：我要调 XX 工具        │
                    └───────────────┬─────────────────┘
                                    │
                    ┌───────────────▼─────────────────┐
                    │  3. 执行工具（真查 MySQL）        │
                    │     把结果作为 role="tool" 回填   │
                    └───────────────┬─────────────────┘
                                    │
                             还不够？ ──是的──▶ 回到第 1 步（最多 5 轮）
                                    │
                                    不是
                    ┌───────────────▼─────────────────┐
                    │  4. 切流式，一段段吐出最终回答    │
                    │     通过 SSE 推给前端（打字机）   │
                    └─────────────────────────────────┘
```

## 关键设计决策（面试常问的就是这些）

### 1. 为什么要看 `finish_reason` 判断，而不是看 `content` 有没有内容

模型决定调工具时，返回的是 `finish_reason: "tool_calls"`，**而 `content` 是 `null`**。
所以如果用"content 有没有值"来判断它要不要调工具，会得出完全相反的结论。
（这是最容易写错的地方，写在 `crud/agent.py` 的注释里了。）

### 2. 工具报错为什么不抛异常，而是返回 `{"error": ...}`

让错误**回到模型手里**：它看到参数写错了就改对，看到查不到就换个关键词。
如果直接抛异常，整个请求就断了，用户看到的是报错页。
这是 Agent 比普通接口更耐用的关键（`tools/registry.py`）。

### 3. 两段式流式：循环阶段非流式，最后一轮才流式

前几轮的目的只是"拿到 tool_calls 或者判断它不需要工具了"，不需要一个字一个字看；
只有**最终回答**才需要打字机效果。
这样既省事（不用解析带工具调用的流式响应），又保证体验。

### 4. 模型会偷懒：不查数据就直接编数字 → 兜底强制它查

**实测发现的问题**：带上下文追问"那科技类有多少篇"时，**3 次里有 1 次模型不调工具，
直接编了个"51 篇"**（真实是 50）。数据查询场景里编数字是致命的。

**三层防护**：
1. **兜底重试**：第一轮发现它没调工具，就带 `tool_choice="required"` 再问一次，
   强制它必须查（`crud/agent.py`）
2. **寒暄判断**：对"你好"这类问题**不**强制 ——
   实测用 `required` 逼"你好"会让模型乱调工具（被逼调了两次，参数还瞎猜）
3. **提示词约束**："数字必须来自本轮工具结果""不要因为上一轮答过就推测"

**结果**：修复前 3 次错 1 次；修复后连测 5 次全部调工具、全部答对。

> 这个"发现模型有概率偷懒 → 加兜底 + 加判断"的过程，本身就是可以讲的一段。

### 5. 工具从 4 个加厚到 7 个，是为了让"模型决策"真的有含金量

一开始只有 4 个工具（数量统计 / 关键词搜索 / 排行榜 / 时间统计），
问题是它们和用户问法**一一对应** —— 问数量就调①，问排行就调③，模型根本不需要决策。
面试官一句话就能问到点上："**这不就是自然语言转 SQL 吗？**"

补的 3 个工具分**两类**，解决的是两个不同的问题（这个区分必须说清，见下）：

**第一类：制造真正的多跳 —— 模型必须组合两个工具**

| 问题 | 模型实际的调用链 |
|---|---|
| "搜一下 AI 的新闻，把最热那篇的内容讲给我听" | `search_news` → `get_news_detail`（**两次调用**） |

关键是 `get_news_detail` **单独用不了**：用户不会直接说新闻编号，
模型只能先搜索或查排行拿到 id，再拿 id 去查详情 —— **拆步骤是它自己的决定**。

**第二类：把复杂计算下沉到代码 —— 一次调用，但内部不简单**

| 问题 | 实际调用次数 | 真正的价值 |
|---|---|---|
| "体育类和科技类哪个更火" | **1 次**（`compare_categories`） | 一次调用内部查两次，并把"谁更火"的**结论算好**（能用代码算准的，别让模型去猜） |
| "最近一周发文量在涨还是在跌" | **1 次**（`get_category_trend`） | 返回**每天一串数**，趋势要模型自己从序列里读出来 |

⚠️ **这两类必须分清** —— 面试官会追问："你说加了工具让模型需要决策，
那我问'哪个更火'，它调几次？"

**诚实答案是一次。** 第二类的价值在"把计算下沉到代码"，不在"逼模型拆步骤"。
把这两件事混着说，被追一句就露怯了。

### 6. 工具结果的长度保护

`MAX_ROUNDS = 8`，每一轮的工具结果都会累加进 messages 再发给模型。
`search_news` 一次最多能返回 20 条 —— 几轮下来上下文会明显膨胀（费钱、还可能超窗口）。

所以 `run_tool` 里有一道统一关卡：结果转成 JSON 超过 6000 字符就**砍列表字段**，
并且**打上 `truncated` 标记** —— 不标记的话模型会以为"库里就只有这几条"，答出错误结论。
（这种坑叫"静默截断"。）

### 7. 配置不能写死（一个真实踩过的坑）

`.env` 里有 `LLM_MODEL`，但代码里实际用的是写死的 `LLM_MODEL_FOR_TOOLS`，
导致**改了 .env 完全没反应**，得翻代码才知道。（这叫"死配置"。）

现在改成：读 .env，但如果配成不支持工具调用的推理模型（`deepseek-reasoner`），
**启动就打印醒目警告并自动回退**，而不是等第一个请求失败才发现。

## 怎么跑起来

### 1. 准备环境

```bash
cd news_agent

# 装依赖
.venv\Scripts\python.exe -m pip install -r requirements.txt

# 复制配置模板，填上你自己的值
copy .env.example .env
```

`.env` 里要填三样：DeepSeek 的 key、本机 MySQL 密码、新闻数据源的 key。

### 2. 建库 + 灌数据

```bash
# 建库建表（自动创建 news_agent 库）
.venv\Scripts\python.exe scripts\init_db.py

# 灌测试数据（400 条，7 个分类）
.venv\Scripts\python.exe scripts\seed_data.py

# 或者：抓真实新闻（需要先去新闻 API 平台申请接口）
.venv\Scripts\python.exe scripts\fetch_news.py
```

### 3. 启动

```bash
.venv\Scripts\python.exe main.py
```

然后打开浏览器：

| 地址 | 是什么 |
|---|---|
| http://127.0.0.1:8020/ | **对话页面**（输入问题，看它调工具、看文字流出来） |
| http://127.0.0.1:8020/docs | 接口文档（给开发调试用） |

### 4. 跑测试

```bash
.venv\Scripts\python.exe -m pytest
```

## 接口

| 方法 | 路径 | 说明 |
|---|---|---|
| GET | `/` | 对话页面 |
| POST | `/api/agent/chat` | 智能体对话（SSE 流式） |
| GET | `/api/agent/stats` | 数据源统计（库里有几条新闻） |
| GET | `/api/agent/health` | 健康检查（服务活着吗、key 配了吗） |

### SSE 事件（前端靠这六类画界面）

| 事件 | 什么时候发 | 带什么 |
|---|---|---|
| `mode` | 开场第一条 | 有哪些工具可用 |
| `tool_call` | 模型决定调工具 | 工具名 + 参数（页面显示"正在查什么"） |
| `tool_result` | 工具执行完 | 查询结果 |
| `delta` | 回答正文 | 一小段文字（会来很多次，就是打字机效果） |
| `done` | 收尾 | 回答字数 + 耗时 + 调了几次工具 |
| `error` | 出错 | 错误说明 |

> 为什么用 SSE 不用 WebSocket：因为**只需要服务端单向推**。
> SSE 就是普通 HTTP，不用换协议、Nginx 直接支持、浏览器还自带重连。
> 另外有个坑：流一旦开始发，HTTP 状态码就改不了了，
> 所以配置类错误必须在开流**之前**拦下来（`routers/agent.py` 里有说明）。

## 数据来源说明

库里现在有 **400 条数据，7 个分类**（体育 / 科技 / 财经 / 娱乐 / 社会 / 国内 / 国际）。

- 默认来自 `scripts/seed_data.py` 生成的**测试数据**（标题按模板 + 随机浏览量/时间，
  用于验证工具调用链路；数据不是真的，但**表结构、索引、SQL 查询全是真实的**）
- `scripts/fetch_news.py` 用来从新闻 API 抓**真实新闻**（需要先在平台申请接口）
- 工具本身不关心数据真假 —— 它查的是 `WHERE category='体育'` 这样的真实 SQL

## 已知的不足（写在这里，面试被问到不用慌）

| 不足 | 如果要改，怎么做 |
|---|---|
| `search_news` 用的是 `LIKE '%关键词%'`，**用不上索引** | 数据量大了换成全文索引或分词检索 |
| 寒暄判断用的是关键词表，中文寒暄是长尾的（"谢谢啦""在么"可能漏） | 漏判的后果只是"多查一次库"，不影响正确性；更干净的做法是交给模型判断 |
| 没有做语义检索（只能关键词匹配） | 接入向量库做语义搜索，作为第 8 个工具 |
| 单机单进程，没有并发压测数据 | 上多 worker + 压测 |

## 和"项目1"的关系

这是第二个项目。项目1 是一个新闻资讯平台后端（含 RAG 问答模块）。

| | 项目1 | 项目2（本项目） |
|---|---|---|
| 数据 | 非结构化：新闻正文 → 向量库 | 结构化：MySQL 表 |
| 模型角色 | **写作的人** —— 检索好喂给它，它照着写 | **做决定的人** —— 它自己决定查什么、查几次 |
| 控制流 | 直线：检索 → 拼提示词 → 生成 | 循环：想 → 调工具 → 看结果 → 再想 |
| 出错时 | 检索没命中 → 降级成普通回答 | 工具报错 / 查空 → 它自己换个做法重试 |

两个项目共用 FastAPI + SQLAlchemy + DeepSeek + SSE 这套技术栈，
但**一个是"检索增强"，一个是"自主决策"，是 LLM 应用的两种典型形态**，
所以彼此独立、不重复。
